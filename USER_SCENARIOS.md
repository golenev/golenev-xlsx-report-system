# Пользовательские сценарии

Документ описывает фактическое поведение текущей версии приложения. Создание и изменение тест-кейса выполняются только в модальном редакторе; таблица используется для просмотра данных и управления статусами активного регресса.

## ✅ UI User Stories

### UI-1. Создание тест-кейса

- Кнопка **Add Row** открывает модальный редактор нового тест-кейса. На широком экране окно занимает 50% ширины, на узких экранах адаптируется вплоть до полноэкранного режима.
- При открытии редактора `Test ID`, `Category / Feature`, `Short Title`, `General Test Status` и `Notes` не заполнены; `Priority` имеет значение `Medium`, `YouTrack Issue Link` содержит базовый префикс, а `Ready Date` показывает текущую дату и недоступна для изменения.
- Редактор детального сценария показывает один пустой корневой шаг, но это исходное состояние не считается пользовательским изменением.
- Для сохранения обязательны непустые `Test ID`, `Category / Feature`, `Short Title` и структурированный `Detailed Scenario` хотя бы с одним содержательным шагом. Пока обязательные данные не заполнены, кнопка **Сохранить** недоступна.
- `Test ID` обрезается по краям и должен быть уникальным. При совпадении с существующей записью показывается предупреждение **Duplicate Test ID**, сохранение не выполняется, а модальный редактор остаётся открытым.
- При успешном сохранении UI отправляет один запрос `POST /api/tests?forceUpdate=true`, закрывает модальное окно, перечитывает таблицу и показывает созданный тест-кейс в отсортированном списке.
- При ошибке сервера модальное окно остаётся открытым, чтобы пользователь мог исправить данные и повторить сохранение.

### UI-2. Фиксация Ready Date

- При создании модальный редактор показывает текущую дату в поле `Ready Date`, но не отправляет её как редактируемое значение: окончательную дату первого сохранения устанавливает сервер.
- При редактировании существующего тест-кейса `Ready Date` также доступна только для чтения.
- Обычный UI-сценарий не изменяет `Ready Date`; серверное изменение возможно только через API с `forceUpdate=true` и явно переданной корректной датой.

### UI-3. Редактирование существующего тест-кейса

- Кнопка **Изменить** в колонке **Детальный сценарий** открывает тот же модальный редактор в режиме изменения существующей записи.
- `Test ID` и `Ready Date` в режиме редактирования недоступны для изменения. Остальные пользовательские поля, включая `Category / Feature`, `Short Title`, `YouTrack Issue Link`, `General Test Status`, `Priority`, `Detailed Scenario` и `Notes`, редактируются в модальном окне.
- При открытии редактора все раскрываемые блоки шагов и вложений находятся в свёрнутом состоянии.
- Изменения отправляются одним запросом после нажатия **Сохранить**. Инлайн-редактирования и сохранения по blur или выбору значения в таблице больше нет.
- UI отправляет изменение с `forceUpdate=true`, поэтому переданные ручные поля могут быть обновлены. При успешном ответе модалка закрывается и таблица перечитывается; при ошибке введённые данные остаются в редакторе.
- `General Test Status` выбирается только из поддерживаемого справочника, `Priority` — из фиксированного набора приоритетов.

### UI-3.1. Просмотр таблицы и детального сценария

- Вне модального редактора все данные тест-кейса в таблице доступны только для чтения. Единственное исключение — колонка **Regress Run** во время активного регресса.
- Колонка **Детальный сценарий** сохраняет интерактивный read-only просмотр: пользователь может независимо раскрывать и сворачивать шаги, подшаги и вложения либо развернуть или свернуть всё дерево одной кнопкой.
- Раскрытие дерева меняет только представление данных и не переводит тест-кейс в режим редактирования.
- Для сценария доступны просмотр текста шагов, параметров, длительности, имён, размеров и содержимого вложений, если соответствующие данные присутствуют.
- Кнопка экспорта в ячейке сценария скачивает текстовое представление тест-кейса с его идентификатором, категорией, названием, шагами, параметрами и вложениями.

### UI-3.2. Редактирование структурированного сценария

- Текст шага редактируется непосредственно в заголовке блока шага; отдельное дублирующее поле описания не показывается.
- Пользователь может добавлять и удалять корневые шаги и подшаги. Нумерация подшагов отображает их вложенность.
- Для каждого шага можно добавить до 10 вложений. Имя вложения редактируется непосредственно в его заголовке без дублирующего текстового представления.
- После раскрытия вложения пользователь может изменить его содержимое в поле, занимающем ширину родительского блока, или удалить вложение.
- Параметры выполнения, полученные из Allure, отображаются только для чтения и при сохранении остаются без изменений.

### UI-3.3. Защита несохранённых изменений модального редактора

- В нижней части модального окна отображается состояние **Нет изменений** или **Есть несохранённые изменения**. Состояние меняется сразу после изменения любого редактируемого значения.
- Если пользователь ничего не изменил, модальное окно закрывается без предупреждения клавишей `Esc`, крестиком или нажатием на затемнённую область вне окна.
- Если есть несохранённые изменения, любой из этих трёх способов показывает предупреждение **Сохранить изменения?** и не закрывает редактор автоматически.
- Действие **Не сохранять** закрывает редактор и отбрасывает черновик: новый тест-кейс не появляется в таблице, а изменения существующего не отправляются.
- Действие **Продолжить редактирование** закрывает предупреждение, сохраняет черновик в модальном окне и позволяет продолжить ввод. Нажатие `Esc` на самом предупреждении имеет тот же эффект.
- Попытка перезагрузить или покинуть страницу при наличии несохранённых изменений вызывает стандартное предупреждение браузера. Для неизменённой модалки такое предупреждение не регистрируется.

### UI-4. Обновление таблицы после удаления

- В текущей табличной форме нет пользовательской кнопки удаления тест-кейса.
- Запись удаляется через `DELETE /api/tests/{testId}`. После обновления страницы или повторной загрузки данных удалённая запись исчезает из таблицы.

### UI-5. Сортировка таблицы

- Для `Test ID`, состоящих из числа и опционального числового суффикса после дефиса, таблица сначала сравнивает основное число, затем суффикс. Для остальных идентификаторов применяется регистронезависимое сравнение с учётом чисел внутри строки.
- Сортировка применяется после первоначальной загрузки, создания, изменения, импорта и повторного получения данных после удаления.

### UI-6. Экспорт данных

- Кнопка **Export to Excel** выгружает актуальные данные таблицы в XLSX с применением ширин колонок из конфигурации.
- Отдельная кнопка в колонке **Детальный сценарий** экспортирует выбранный тест-кейс и его структурированный сценарий в текстовый файл.

### UI-7. Управление регрессом

- В заголовке колонки **Regress Run** находится управление регрессионным прогоном.
- Для запуска требуется непустое имя релиза. Сервер отклоняет запуск, если уже есть активный регресс или имя релиза использовалось ранее.
- Пока регресс имеет статус **RUNNING**, только колонка **Regress Run** доступна для изменения непосредственно в таблице. Для каждой строки выбирается `PASSED`, `FAILED` или `SKIPPED`; остальные колонки остаются read-only.
- Ручные изменения статусов хранятся на странице до завершения регресса. При попытке остановить прогон с незаполненным статусом хотя бы у одного тест-кейса UI показывает предупреждение и не отправляет запрос завершения.
- Успешная остановка сохраняет полный снимок текущих тест-кейсов и их статусов, после чего колонка **Regress Run** снова блокируется.
- Отмена пустого запуска удаляет запись регресса. Если в активном регрессе уже накоплены результаты, например после загрузки Allure, отмена переводит запись в **COMPLETED** и сохраняет накопленный payload; UI в обоих случаях возвращается в состояние без активного прогона.

### UI-8. Загрузка результатов Allure через UI

- Пользователь выбирает директорию `allure-results`, видит имя папки и количество выбранных файлов, после чего отдельно подтверждает загрузку.
- UI отправляет все файлы и их относительные пути multipart-запросом `/uploadReport`, передавая фактическое значение `isRegressRunning`.
- Обычная UI-загрузка не передаёт `forceUpdate`, поэтому используется значение `false`: у существующего тест-кейса обновляются обязательные данные из отчёта (`category`, `shortTitle`, `scenario`), а ручные поля и `Ready Date` сохраняются.
- Для нового тест-кейса из Allure сервер создаёт обязательные данные из отчёта и применяет серверные значения по умолчанию для ручных полей и даты.
- Во время активного регресса отчёт должен содержать валидный `runStatus` для каждого импортируемого тест-кейса. Статусы записываются в колонку **Regress Run** и синхронизируются с payload текущего регресса.
- После успешного импорта UI перечитывает таблицу и состояние регресса. Ошибка выбора, парсинга, валидации или сохранения отображается пользователю без очистки существующих данных таблицы.

### UI-9. Аналитика по релизам

- Виджет **Release Analytics** загружает список релизов через `/api/regressions/releases`, автоматически выбирает первый доступный релиз и получает его снимок через `/api/regressions/{releaseId}`.
- В свёрнутом состоянии виджет показывает краткую сводку; после раскрытия пользователь может выбрать другой релиз.
- Для выбранного снимка отображаются процент автоматизации по статусу `Готово`, количество `Passed` и `Failed`, а также исходный payload снапшота со всеми тест-кейсами и их статусами.
- Пользователь может скачать XLSX-снимок выбранного релиза. При ошибке доступны сообщение и повторная загрузка; при пустом списке отображается **Нет доступных релизов**.

### UI-10. Конфигурация подписей и ширин

- При загрузке таблицы UI получает от сервера ширины колонок и словарь переводов.
- Настроенные переводы применяются к поддерживаемым заголовкам и элементам управления главной страницы; для отсутствующего ключа используется исходный текст.
- Ширина **Детального сценария** дополнительно ограничивается интерфейсом, чтобы раскрытое дерево не делало таблицу неуправляемо широкой.

## ✅ API User Stories

### API-1. Получение списка тестов

- `GET /api/tests` возвращает отсортированный список тест-кейсов, объект `columnConfig` с ширинами колонок и объект `translations` с подписями для UI.
- Сценарий каждого тест-кейса возвращается в структурированном виде. Сохранённые записи старого текстового формата преобразуются сервером в структуру шагов.

### API-2. Создание или обновление одного тест-кейса

- `POST /api/tests?forceUpdate={true|false}` выполняет upsert по нормализованному `testId`; идентификатор обязателен, обрезается по краям и не изменяется у существующей записи.
- Для новой записи обязательны `category`, `shortTitle` и непустой структурированный `scenario`. При обновлении существующей записи одиночный endpoint допускает отсутствие этих полей и использует сохранённые значения как fallback.
- Переданные `category`, `shortTitle` и `scenario` обновляются независимо от `forceUpdate`.
- При создании сервер заполняет отсутствующие значения по умолчанию: `readyDate` — текущая дата, `issueLink` — базовый префикс, `generalStatus` — `Готово`, `priority` — `Medium`, `notes` — пустая строка; `updatedAt` устанавливается в текущее время.
- Ручные поля (`issueLink`, `generalStatus`, `priority`, `notes`) существующей записи меняются только при `forceUpdate=true` и наличии соответствующего поля в запросе.
- `readyDate` изменяется только при `forceUpdate=true` и явно переданной дате в ISO-формате. Значения `generalStatus` и `priority` валидируются по справочникам.
- Одиночный endpoint не включает режим регресса: переданный `runStatus` не применяется.

### API-3. Пакетная загрузка

- `POST /api/tests/batch?isRegressRunning={true|false}&forceUpdate={true|false}` атомарно создаёт или обновляет непустой список тест-кейсов.
- В отличие от одиночного upsert, каждый элемент batch-запроса должен содержать собственные `category`, `shortTitle` и непустой `scenario`; fallback из существующей записи для обязательных полей не используется.
- `forceUpdate` управляет ручными полями и явно переданной `readyDate` по тем же правилам, что и одиночный endpoint.
- При `isRegressRunning=true` сервер требует активный регресс текущей даты, валидный `runStatus` у каждого элемента и синхронизирует полученные статусы с payload регресса. При отсутствии активного прогона возвращается 404.
- При `isRegressRunning=false` поле `runStatus` игнорируется.

### API-4. Обработка совпадающего Test ID

- Передача существующего `testId` является командой обновления, а не ошибкой дубликата. `testId` остаётся неизменным, а остальные поля применяются по правилам endpoint и его параметров.
- UI создания предварительно запрещает такой запрос и показывает **Duplicate Test ID**, чтобы пользователь случайно не обновил существующий тест-кейс вместо создания нового.
- Отсутствующий или пустой `testId` возвращает 400 с сообщением `Required field testId is missing`.

### API-5. Управление Ready Date

- При создании без разрешённой явно переданной даты `readyDate` устанавливается сервером в текущую дату.
- При обновлении дата принимается только с `forceUpdate=true` и в ISO-формате; без флага переданное значение игнорируется, а существующая дата сохраняется.
- Некорректный формат разрешённой к обновлению даты возвращает 400 `Invalid readyDate format`.

### API-6. Управление регрессом и ручными полями при upsert

- `forceUpdate` применяется к одиночному, пакетному и upload-endpoint и управляет только `issueLink`, `generalStatus`, `priority`, `notes` и явно переданной `readyDate`.
- Создание и редактирование через модальный UI используют `forceUpdate=true`.
- Загрузка Allure через текущий UI не передаёт `forceUpdate`, поэтому endpoint использует `false` и сохраняет ручные поля существующих записей.
- `isRegressRunning` доступен только для batch- и upload-сценариев и влияет на обязательность, сохранение и синхронизацию `runStatus`.

### API-7. Удаление тест-кейса

- `DELETE /api/tests/{testId}` удаляет найденную запись; при отсутствии тест-кейса возвращается 404.

### API-8. Экспорт в Excel

- `GET /api/tests/export/excel` возвращает XLSX с актуальными тест-кейсами и ширинами колонок из серверной конфигурации.
- Если значение любого экспортируемого поля превышает лимит Excel в 32 767 символов на ячейку, оно без потерь разбивается на несколько расположенных по вертикали ячеек с убранными внутренними границами; остальные колонки тест-кейса объединяются по высоте этих строк, чтобы запись визуально оставалась единым блоком.

### API-9. Управление регрессом

- `POST /api/regressions/start` запускает прогон: имя релиза обязательно, обрезается по краям, должно быть уникальным, а другой регресс не должен находиться в статусе **RUNNING**.
- `POST /api/regressions/stop` принимает непустую карту `testId -> status`, допускает только `PASSED`, `FAILED` и `SKIPPED` и требует результат для каждого актуального тест-кейса.
- Успешная остановка переводит регресс в **COMPLETED** и сохраняет полный снимок тест-кейсов с метаданными релиза и статусами прогона.
- `POST /api/regressions/cancel` при отсутствии активного прогона идемпотентно возвращает **IDLE**. Пустой активный прогон удаляется; прогон с накопленным payload переводится в **COMPLETED** с сохранением данных.

### API-9.1. История регрессов

- `GET /api/regressions/releases` возвращает релизы с `id`, именем, датой и статусом, отсортированные по дате убывания.
- `GET /api/regressions/{regressionId}` возвращает метаданные и сохранённый payload указанного регресса; для неизвестного ID возвращается 404.
- `GET /api/regressions/{regressionId}/snapshot.xlsx` скачивает XLSX выбранного снимка; пустой payload возвращает 400.

### API-10. Текущее состояние регресса

- `GET /api/regressions/current` возвращает активный прогон в статусе **RUNNING**, включая дату, имя релиза и уже накопленную карту результатов.
- Если активного прогона нет, endpoint возвращает **IDLE** и текущую дату. Завершённые прогоны доступны через endpoints истории; **COMPLETED** возвращается непосредственно ответом успешной остановки или отмены прогона с накопленными данными.

### API-11. Конфигурация колонок

- `GET /api/config/columns` возвращает объект конфигурации с `columns` и `translations`.
- Backend загружает конфигурацию при инициализации и хранит её в памяти. Публичного endpoint для reload нет, поэтому после изменения `config/column-config.json` требуется перезапуск backend-контейнера или приложения.
