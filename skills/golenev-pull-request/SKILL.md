# Pull request Golenev

## Основное правило

Создавать PR как человекочитаемую передачу законченной работы пользователю на проверку. Писать заголовок и описание на русском языке. Описывать по пунктам, что фактически сделано и как это проверено.

Не мержить созданный PR. Оставлять финальную проверку и merge пользователю. Выполнять merge только по отдельному явному поручению, полученному после или вместо запроса на создание PR.

## Подготовка

Перед созданием или обновлением PR:

1. Определить текущую head-ветку и фактическую base-ветку; не считать `main` базой без проверки.
2. Проверить `git status` и не включать чужие, временные или не относящиеся к задаче изменения.
3. Изучить полный diff ветки относительно base, а не только последний commit.
4. Изучить список commits ветки и сопоставить его с исходной задачей и последующими уточнениями пользователя.
5. Проверить наличие PR для той же head-ветки. Обновлять существующий PR вместо создания дубликата.
6. Убедиться, что предназначенные для PR commits отправлены в remote.

Использовать GitHub CLI или доступный GitHub-инструмент. Не изменять внешнее состояние, кроме действий, необходимых для запрошенного PR.

## Заголовок

- Формулировать краткий результат работы на русском языке.
- Описывать изменение поведения или назначение работы, а не процесс написания кода.
- Не использовать бессодержательные названия: «Исправления», «Обновление», «Новые изменения».
- Не добавлять номер задачи, тип или префикс, если этого не требует репозиторий или пользователь.

Пример: `Добавление UI-тестов закрытия модального редактора`.

## Описание

Писать конкретно, простым русским языком и по пунктам. По умолчанию использовать структуру:

```markdown
## Что сделано

- Добавлено ...
- Изменено ...
- Удалено ...

## Проверка

- `команда проверки` — успешно.
- Тесты не запускались: причина.
```

Добавлять раздел `## Что проверить` только при наличии важных ручных проверок, ограничений или рисков:

```markdown
## Что проверить

- Убедиться, что ...
```

## Содержание пунктов

- Группировать изменения по пользовательскому поведению, бизнес-смыслу или законченным техническим результатам.
- Описывать все значимые части diff, включая восстановленные атрибуты, изменённые тестовые сценарии, документацию и конфигурацию.
- Не превращать описание в перечень файлов, классов или commits без объяснения результата.
- Не копировать исходную постановку задачи как будто она уже выполнена.
- Не заявлять о проверке, которую фактически не запускали.
- Указывать точную команду и результат выполненной проверки.
- Если тест не удалось запустить, прямо указывать причину и не маскировать её общей фразой.
- Не включать внутренние рассуждения агента, случайные промежуточные попытки и несущественные детали реализации.

## Готовность PR

- Создавать обычный ready-for-review PR, если работа завершена и пользователь не просил draft.
- Создавать draft только по прямому запросу или когда пользователь явно поручил открыть незавершённую работу.
- После новых commits обновлять описание существующего PR, если фактический scope перестал ему соответствовать.
- Перед передачей повторно сверять заголовок и каждый пункт с diff base...head.

## Передача пользователю

После успешного создания или обновления сообщить:

- ссылку на PR;
- head-ветку;
- краткий итог выполненных проверок;
- явно, что PR оставлен пользователю для проверки и merge.

Не предлагать и не выполнять merge автоматически.

## Финальная самопроверка

- Заголовок написан по-русски и описывает результат.
- Раздел «Что сделано» содержит человекочитаемые конкретные пункты.
- Описание покрывает весь diff ветки, а не только последнюю правку.
- Раздел «Проверка» соответствует реально выполненным действиям.
- Ограничения и ручные проверки указаны без сокрытия.
- Для head-ветки не создан дублирующий PR.
- PR готов к пользовательскому review и не смержен.
