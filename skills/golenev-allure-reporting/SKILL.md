# Allure-шаги и отчёт Golenev

## Роль Allure-отчёта

Считать Allure-отчёт единственным человекочитаемым источником правды о тест-кейсе. Не поддерживать отдельное ручное описание сценария: код теста должен порождать понятную исполняемую спецификацию и доказательства её выполнения.

Помнить, что исполняемым источником отчёта остаётся код конкретной версии. Сохранять стабильный `@AllureId` и связь отчёта со сборкой и commit, чтобы результат нельзя было ошибочно трактовать вне контекста версии приложения.

Строить отчёт как маршрут тестового субъекта по бизнес-состояниям, а не как маршрут тестового кода по инфраструктуре.

## Тестовый субъект

Определять перед написанием теста один тестовый субъект — объект или процесс, вокруг которого построен смысл проверки. Например: тест-кейс с конкретным `testId`, запуск регресса с конкретным release name или процесс batch-импорта.

- Использовать ровно один тестовый субъект в каждом тесте.
- Называть субъект однозначно в `@DisplayName` и шагах, когда без этого маршрут неясен.
- Описывать шагами изменение состояния субъекта, воздействие на него или наблюдение его результата.
- Разделять сценарий на разные тесты, если в нём появились два независимых субъекта с самостоятельными маршрутами и результатами.
- Считать batch одним субъектом-процессом, если проверяется поведение batch целиком, а не независимые истории отдельных записей.

## Уровни абстракции отчёта

Строить отчёт сверху вниз:

1. `@DisplayName` класса — область или feature.
2. `@DisplayName` теста — маршрут тестового субъекта и ожидаемый итог.
3. `@AllureId` — стабильная идентичность самостоятельного тест-кейса.
4. `step("...")` в тестовой функции — обязательные бизнес-состояния и переходы субъекта.
5. `@Step` в Page Object, DAO, transport или service — вложенные технические операции, реализующие бизнес-переход.
6. UI/API attachments — фактические доказательства и детали диагностики.

Не считать вложенность бизнес-шаг → технический `@Step` дублированием. Верхний шаг отвечает на вопросы «что происходит с субъектом?» и «зачем?», вложенный — «как это сделано?». Раскрытие вложенности должно дополнять картину, не повторять её теми же словами.

## Метаданные теста

- Писать `@DisplayName` на русском в форме наблюдаемого поведения.
- Назначать один уникальный `@AllureId` каждому самостоятельному `@Test`.
- Проверять существующие ID перед добавлением нового.
- Не объединять разные варианты параметризацией, если им нужны разные Allure ID.
- Не менять существующий Allure ID при рефакторинге поведения того же тест-кейса.

## Обязательные бизнес-шаги в тесте

Использовать `org.golenev.utils.step` в каждой тестовой функции. Не оставлять внутри `@Test` голые вызовы Page Object, DAO, service или assertions без охватывающего бизнес-шага.

- Формулировать шаг глаголом во множественном числе: «Открываем», «Создаём», «Изменяем», «Отправляем», «Проверяем», «Удаляем».
- Описывать состояние или переход тестового субъекта, а не выполнение кода: не писать «Вызываем DAO», «Кликаем по CSS-селектору», «Парсим JSON».
- Включать значимый идентификатор: testId, поле, release name или способ закрытия.
- Помещать assertions внутрь шага «Проверяем...», чтобы падение имело бизнес-контекст.
- Возвращать данные из шага вместо скрытой mutable-переменной.
- Не добавлять верхнеуровневый шаг на каждую вызываемую функцию.

```kotlin
val response = step("Отправляем batch без обязательного поля $field") {
    reportService.sendBatch(request, expectedStatus = 400)
}

step("Проверяем, что batch отклонён из-за отсутствия поля $field") {
    response.statusCode.shouldBe(400, "response.statusCode не совпало с ожидаемым")
}
```

## Семантическая группировка

Объединять несколько технических действий в один бизнес-шаг, если вместе они образуют один понятный переход субъекта в новое состояние.

```kotlin
step("Создаём тест-кейс через модальный редактор") {
    mainPage.testCaseTable.openCreateEditor()
    mainPage.testCaseTable.fillTestId(testId)
    mainPage.testCaseTable.fillCategory(testCase.category.orEmpty())
    mainPage.testCaseTable.fillShortTitle(testCase.shortTitle.orEmpty())
    mainPage.testCaseTable.fillIssueLink(testCase.issueLink.orEmpty())
    mainPage.testCaseTable.selectGeneralStatus(testCase.generalStatus.orEmpty())
    mainPage.testCaseTable.selectPriority(testCase.priority.orEmpty())
    mainPage.testCaseTable.fillDetailedScenarioSteps(testCase.scenario?.steps.orEmpty())
}
```

Ожидать, что каждый вызванный метод Page Object имеет свой более технический `@Step`. Разбивать верхний шаг, когда:

- изменилось бизнес-состояние субъекта;
- возникла отдельная бизнес-развилка или решение пользователя;
- требуется самостоятельная проверка наблюдаемого результата;
- группа стала скрывать несколько смысловых действий под одним общим названием.

Не создавать гигантский шаг на весь тест. На свёрнутом уровне должны быть видны последовательные состояния субъекта, а не один контейнер со всей реализацией.

## Технические `@Step`

- Аннотировать reusable actions Page/Component Object, DAO, transport и service.
- Описывать конкретную техническую операцию и её результат, достаточные для диагностики после раскрытия бизнес-шага.
- Подставлять аргументы через `{parameterName}`.
- Не повторять дословно название внешнего бизнес-шага.
- Не использовать один `@Step`-метод с `when`, если отчёт должен явно показать разные пользовательские действия.
- Делать отдельные методы `closeEditorByEscape`, `closeEditorByCloseButton`, `closeEditorByBackdropClick`.
- Не скрывать финальный выбор пользователя внутри общей Template-функции теста.

## Setup и cleanup

- Не засорять основной маршрут субъекта инфраструктурной подготовкой, не влияющей на его бизнес-состояние.
- Показывать setup как бизнес-шаг, если он создаёт или переводит тестовый субъект в необходимое состояние.
- Оборачивать технические fixture и cleanup в диагностируемые шаги, если их результат важен для разбора падения.
- Формулировать cleanup относительно субъекта, когда он удаляет или завершает его: «Удаляем созданный тест-кейс $testId».

## Человекочитаемые UI-вложения

Использовать существующий `ReadableAllureSelenideListener` через `DriverConfig().setup()`.

- Назначать элементам `.name(alias)`; registry связывает alias с нормализованным locator в текущем потоке.
- Добавлять `.because(reason)` к Selenide condition.
- Ожидать в attachment alias, конечный locator, тип CHECK/ACTION, operation, success condition, because, status и error.
- Не включать стандартные шумные Selenide steps: listener уже сохраняет screenshot/page source и формирует текстовые attachments.
- Очищать `UiElementNameRegistry` при настройке каждого драйвера.

```kotlin
private val modal = `$`("[data-testid='test-case-editor-modal']")
    .name("Модальный редактор тест-кейса")

modal.shouldBe(
    visible.because("после Add Row должен открыться редактор создания")
)
```

## API-вложения

- Пропускать все Rest Assured requests через `BaseSpecification.prepareForRequest`.
- Сохранять фильтр `AllureRestAssured()` для request/response attachments.
- Валидировать status централизованно, затем добавлять бизнес-проверки в тесте.
- Для UI-запроса, перехваченного proxy, парсить body в DTO и сравнивать внутри отдельного шага.
- Не вставлять длинный JSON в имя шага; сохранять его как attachment или проверять через DTO.

## Template и отчёт

- Называть общую функцию с постфиксом `Template`.
- Передавать вариантное действие лямбдой и отдельное человекочитаемое описание.
- Оставлять в Template только общую часть бизнес-маршрута.
- Размещать уникальную концовку прямо в тестовом методе, чтобы Allure показывал точный сценарий.
- Следить, чтобы Template не скрывал единственный тестовый субъект и обязательные верхнеуровневые шаги.

## Критерии качества

Проверять отчёт в трёх масштабах:

1. На свёрнутом уровне `@DisplayName` и бизнес-шаги полностью описывают тест-кейс без чтения исходного кода.
2. После раскрытия шага видны технические действия Page Object, DAO или API, объясняющие реализацию бизнес-перехода.
3. Attachments позволяют доказать фактическое действие и диагностировать падение.

Дополнительно убедиться, что:

- в тесте можно назвать ровно один тестовый субъект;
- каждый верхний шаг описывает его состояние, переход или наблюдаемый результат;
- по последовательности шагов понятны предусловие, действие и ожидаемый итог;
- каждый UI locator имеет alias, а важная condition — `because`;
- assertions содержат фактическое выражение и понятное сообщение;
- cleanup виден или однозначно диагностируется;
- Allure ID не дублируются;
- целевой тест проверен по `build/allure-results` или сгенерированному report, а не только по консоли Gradle.
