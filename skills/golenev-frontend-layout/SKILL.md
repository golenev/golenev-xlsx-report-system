# Вёрстка frontend Golenev

## Цель

Развивать интерфейс как продолжение существующего приложения, даже если пользователь описал только бизнес-возможность. Самостоятельно учитывать визуальные паттерны, состояния, адаптивность, семантику и стабильные `data-*` контракты; не требовать отдельного напоминания о каждом из них.

Перед изменением вёрстки полностью прочитать [references/layout-patterns.md](references/layout-patterns.md).

## Обязательный маршрут изучения

1. Прочитать релевантный раздел `USER_SCENARIOS.md` и определить текущее пользовательское поведение.
2. Найти компонент, который владеет состоянием функции, и ближайший визуальный аналог в `frontend/src`.
3. Найти все CSS-правила аналога, включая поздние переопределения и `@media`; не делать вывод по первому совпадению селектора.
4. Найти использование затрагиваемых `data-*`, `aria-*`, class names и текста в `e2e-test/src/main/kotlin` и `e2e-test/src/test/kotlin`.
5. Зафиксировать состояния новой функции: исходное, открытое, выбранное, пустое, loading, disabled, error и mobile — только те, которые возможны по сценарию.
6. Если прямого аналога нет, явно пометить это как предположение и собрать решение из существующих примитивов, а не вводить отдельный визуальный стиль.

## Границы изменения

- Сохранять существующее поведение вне запрошенной функции. Не превращать read-only таблицу в редактируемую и не переносить редактирование из модального окна без отдельного требования.
- Размещать состояние рядом с компонентом, которому оно принадлежит. Выносить компонент, если блок имеет собственное состояние, несколько действий или повторно используется.
- Не подключать новую UI-библиотеку, CSS-фреймворк, набор иконок или шрифт, если задачу можно решить текущими React/CSS-паттернами.
- Не создавать второй вариант существующего примитива. Переиспользовать `primary-btn`, `secondary-btn`, `ghost-btn`, `success-btn`, `danger-btn`, `icon-button` и feature-классы либо обоснованно расширять их.
- Не использовать inline styles для постоянного оформления. Оставлять их только для фактически динамических значений, как текущие ширины колонок и цвета status chip.
- Давать новым feature-классам понятный kebab-case префикс компонента: `table-filter-*`, `test-case-modal-*`, `scenario-*`, `analytics-*`.
- Стили компонента держать рядом одним блоком в `styles.css`; адаптивные правила располагать после базовых правил этого блока.

## Визуальная система

- Использовать текущий системный шрифт `Inter` с системными fallback.
- Строить поверхности на белом и светло-сером фоне, с холодными серыми границами, синим акцентом и мягкими тенями.
- Сохранять компактный масштаб: основной текст 13–14 px, подписи 11–12 px, заголовки 15–22 px.
- Использовать существующую иерархию поверхностей: фон страницы → карточка/таблица → вложенная секция → поле или строка.
- Использовать существующую геометрию: небольшие поля и строки 6–8 px, контролы 7–10 px, карточки и модалки 10–14 px, pill-счётчики `999px`.
- Для focus использовать синюю границу и мягкий outline; для hover менять фон или тень без скачка размеров.
- Для disabled одновременно задавать нативный `disabled`, визуальное состояние и `data-disabled="true"`.
- В flex/grid-контейнерах с пользовательским текстом задавать `min-width: 0`; для полей — `width: 100%` и `box-sizing: border-box`.

## Таблица и функции наподобие Excel-фильтров

- Сохранять sticky-header, горизонтальный scroll и серверные ширины колонок.
- Размещать управление конкретной колонкой внутри её `header-content`/`header-title`; идентифицировать колонку через `data-name`.
- Оформлять компактный dropdown/popover по аналогии с `status-options`: белая поверхность, тонкая граница, радиус, мягкая тень, список действий и явные hover/focus состояния.
- Отделять выбор значений от применения, очистки и закрытия, если пользователь может сделать множественный выбор.
- Показывать активный фильтр наблюдаемым состоянием кнопки и `data-state`, а не только цветом.
- Не связывать фильтрацию с редактированием ячеек. Скрывать или группировать строки на уровне отображаемого набора данных, сохраняя исходные записи.
- Определять поведение пустого результата, сброса одного фильтра, сброса всех фильтров, комбинации нескольких колонок и появления новых данных после reload.
- Делать trigger и popover доступными с клавиатуры; задавать `aria-expanded`, доступное имя и связь с панелью через `aria-controls`, когда применимо.

## Контракт `data-*`

Добавлять атрибуты как часть реализации каждого нового интерактивного блока:

- `data-testid` — стабильный тип элемента или уникальный control: `table-filter-button`, `table-filter-panel`, `table-filter-option`. Не включать переводимый текст и случайный индекс.
- `data-role` — структурная роль: `button`, `input`, `field`, `widget`, `card`, `table`, `header`, `headercell`, `row`, `cell`.
- `data-name` — бизнес-имя поля, колонки или виджета. Для повторяемых колонок использовать то же логическое имя, которое уже возвращает `getColumnDataName`.
- `data-action` — действие в форме глагола: `open-filter`, `toggle-filter-value`, `apply-filter`, `clear-filter`.
- `data-test-case-id`, `data-scenario-path`, `data-id` — стабильная идентичность экземпляра. Не зашивать идентификатор строки в `data-testid`.
- `data-state`, `data-disabled`, `data-loading`, `data-value` — наблюдаемое состояние. Булевы значения передавать строками `"true"`/`"false"` через существующий helper.

Сохранять существующие атрибуты и их значения при рефакторинге. Перед переименованием или удалением обязательно доказать через `rg`, что контракт не используется Page Object, тестом, CSS или внешней интеграцией. `aria-*` и нативные роли добавлять независимо от тестовых атрибутов: `data-*` не заменяют доступность.

## Адаптивность и слои

- Проверять desktop, промежуточную ширину и mobile. Ориентироваться на существующие переходы около 1000/900, 640/600 px.
- Сначала сохранять читаемость и доступ к действиям, затем плотность. На mobile разрешать одну колонку, полноэкранную модалку и вертикальные action-группы.
- Для overlay использовать отдельные layer/backdrop/dialog, фиксированное позиционирование, явный `z-index`, блокировку scroll body и независимую прокрутку content.
- Не растягивать родительский toggle ради ширины вложенного поля. Ограничивать ширину на непосредственном контейнере и контроле.
- Не обрезать focus ring, dropdown или modal actions через необоснованный `overflow: hidden`.

## Проверка

1. Проверить diff JSX/CSS и убедиться, что не удалены существующие hooks автоматизации.
2. Выполнить `npm.cmd test` и `npm.cmd run build` в `frontend`.
3. Выполнить `npm.cmd run lint`, если задача не заблокирована уже существующими lint-ошибками; честно сообщить результат.
4. При изменении существующего UI-контракта запустить релевантные UI-тесты и проверить Page Object.
5. Визуально проверить все изменённые состояния на desktop и mobile, если приложение можно запустить.
6. Выполнить `git diff --check` и не добавлять `node_modules`, `dist`, screenshots и другие generated-файлы.

## Финальная самопроверка

- Новая функция выглядит частью существующего интерфейса, а не отдельным дизайн-проектом.
- Все возможные состояния имеют разметку и понятное визуальное отличие.
- Управление работает мышью и клавиатурой, а focus остаётся видимым.
- На узком экране нет недоступных действий и горизонтального выезда модалки.
- Каждый важный элемент имеет осмысленные `data-*`; существующие тестовые контракты сохранены.
- Изменение не открыло запрещённое редактирование и не изменило соседний пользовательский сценарий.
