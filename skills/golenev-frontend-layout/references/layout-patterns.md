## Карта компонентов

| Область | JSX/TSX | Основные CSS-префиксы |
|---|---|---|
| Каркас страницы, actions и таблица | `App.jsx` | `app-*`, `header-*`, `report-table`, `cell-*`, `regression-*` |
| Модальное создание и редактирование | `TestCaseEditorModal.jsx` | `test-case-modal-*`, `unsaved-confirm-*` |
| Редактор сценария | `ScenarioEditor.jsx` | `scenario-editor-*`, `scenario-step-*`, `scenario-attachment-*` |
| Read-only дерево сценария | `ScenarioTree.jsx` | `scenario-tree-*`, `scenario-chevron-*`, `scenario-preview` |
| Аналитика релизов | `ReleaseAnalyticsWidget.tsx` | `release-analytics-*`, `analytics-*`, `snapshot-*`, `donut-*` |

В `App.jsx` остаётся legacy-разметка `newItems`. Не копировать её как актуальный сценарий создания без проверки реального entry point: текущая кнопка **Add Row** открывает `TestCaseEditorModal`.

- Фон страницы: `#f1f3f4`; поверхности: `#fff`; вложенные области: `#f8f9fa`, `#f8fafc`, `#f5f7fa`.
- Границы: `#dadce0`, `#dce1e8`, `#dfe3e8`, `#e5e7eb`.
- Основной синий акцент и focus: `#0a84ff`, `#0969da`, `#0a66c2`.
- Успех: `#34a853`/`#10b981`; опасность: `#d93025`/`#b42318`/`#ef4444`.

## Примитивы

### Кнопки

- `primary-btn` — основное выделенное действие с синим фоном и тенью.
- `secondary-btn` — нейтральное подтверждение или обычное действие.
- `ghost-btn` — тихое utility-действие без рамки.
- `success-btn` — позитивное сохранение в компактной форме.
- `danger-btn` — опасное или регрессионное действие.
- `icon-button` — компактная квадратная utility-кнопка.
- Feature-кнопки (`scenario-link-action`, `scenario-danger-action`, `scenario-add-root`) использовать только внутри соответствующего визуального контекста.

Для каждой кнопки сохранять `type="button"`, disabled-состояние, hover/focus и доступное имя. Не задавать кликабельность обычному `div`, если подходит `button`.

### Поля

- Табличные поля: `cell-input`, `cell-textarea`; сохранённые строки read-only.
- Модальные поля: белый фон, `1px` холодно-серая граница, радиус `7px`, padding `9px 10px`, синий focus outline.
- Controlled React input изменять через `onChange`; textarea разрешать вертикальный resize только там, где это не ломает контейнер.
- Label строить как контейнер поля со вложенным `span`; wide-поле занимает все колонки через feature-класс.
- Disabled-поле должно оставаться читаемым, а не маскироваться только opacity.

### Поверхности

- Простая карточка: белый фон, граница, радиус `10–12px`, мягкая тень.
- Вложенная карточка: меньший padding и более слабая тень.
- Dropdown/popover: absolute относительно trigger-контейнера, белый фон, граница, радиус `8px`, тень, высокий локальный `z-index`.
- Ошибка: светло-красный фон и граница, тёмно-красный текст.
- Loading: skeleton для сложного виджета, текстовый loader для всей таблицы.

## Таблица

- `.table-wrapper` владеет прокруткой и рамкой.
- `.report-table` имеет `width: max-content` и `min-width: 100%`; ширины обычных колонок поступают с backend.
- `thead` sticky и остаётся над строками.
- Ячейка идентифицируется комбинацией `data-testid="test-case-cell"` и `data-name`; строка — `data-testid="test-case-row"` и `data-test-case-id`.
- `Detailed Scenario` имеет отдельное ограничение ширины и read-only интерактивное дерево.
- `Regress Run` является единственным разрешённым inline-control во время активного регресса.

Для нового управления колонкой сохранять структуру `header-content` → `header-title`, не разрушать вычисляемую ширину `<th>` и не помещать popover внутрь scroll-контейнера без проверки clipping.

## Модальные окна

Структура текущего редактора:

```text
test-case-modal-layer
  test-case-modal-backdrop
  test-case-modal
    test-case-modal-header
    test-case-modal-content
    test-case-modal-footer
  unsaved-confirm-layer
```

- Desktop: `50vw`, ограничение viewport, высота до `88vh`.
- До 900 px: фиксированное доступное ограничение ширины.
- До 600 px: полноэкранный режим, одна колонка формы, вертикальные actions подтверждения.
- Header/footer не прокручиваются; content имеет собственный vertical scroll.
- Backdrop является отдельным sibling, поэтому клик вне диалога не смешивается с кликами внутри.
- При открытой модалке scroll body блокируется.

Новый modal workflow должен повторять эту структуру, если нет требования изменить общий modal primitive.

## Сценарий

- Read-only дерево и редактор — разные режимы и разные компоненты.
- Раскрытие дерева не включает редактирование.
- В редакторе заголовок шага и имя вложения одновременно являются редактируемыми полями; не дублировать их отдельным заголовком.
- Вложенность показывается отступом и левой линией, счётчики — pill-элементами.
- Chevron использует `scenario-chevron` и variant-класс; состояние отражается классом `expanded` и `aria-expanded`.
- Вложенные textarea растягивать по непосредственному родительскому блоку. Не расширять ради этого `.scenario-step-toggle`.

В `styles.css` существуют более ранние legacy-правила `scenario-*` и поздние актуальные переопределения. Всегда искать все совпадения селектора и учитывать каскад.

## Data-атрибуты

| Атрибут | Назначение | Пример |
|---|---|---|
| `data-testid` | Стабильный тип или уникальный control | `test-case-editor-modal`, `scenario-step-toggle` |
| `data-role` | Структурная роль | `button`, `field`, `headercell`, `row`, `cell`, `widget` |
| `data-name` | Бизнес-имя поля/колонки/виджета | `Ready Date`, `releaseId` |
| `data-action` | Пользовательское действие | `add-row`, `select-release`, `save-test-case` |
| `data-test-case-id` | Идентичность строки | фактический `testId` |
| `data-scenario-path` | Идентичность узла сценария | `0.1` |
| `data-id` | Идентичность другого доменного экземпляра | release ID |
| `data-state` | Состояние компонента | `draft`, `open`, `filtered` |
| `data-disabled` | Наблюдаемая блокировка | `true`/`false` |
| `data-loading` | Наблюдаемая загрузка | `true`/`false` |
| `data-value` | Значение повторяемой option | status/filter value |

Не подменять `aria-label`, `aria-expanded`, `aria-modal`, `aria-labelledby` или нативный `disabled` тестовыми атрибутами.

## Рецепт нового фильтра колонки

Для запроса «сделать фильтрацию как в Excel» использовать существующие паттерны так:

1. В `App` хранить фильтры отдельно от исходных `items`; строить отображаемый набор через `useMemo` до сортировки/группировки.
2. В заголовок каждой поддерживаемой колонки добавить компактный `button` с `data-testid="table-filter-button"`, `data-role="button"`, `data-name={columnDataName}`, `data-action="open-filter"`, `data-state` и `aria-expanded`.
3. Панель назвать `table-filter-panel`; визуально опереться на `status-options`, но использовать feature-префикс и не менять status dropdown.
4. Повторяемые значения пометить `data-testid="table-filter-option"` и `data-value`; действия применения/сброса — отдельными `data-action`.
5. Сохранить read-only ячейки, sticky header, ширины колонок и поведение `Regress Run`.
6. Обработать несколько фильтров, пустой результат, очистку, обновление данных и keyboard/outside-click lifecycle.
7. Добавить или обновить Page Object и UI-тесты, если функция входит в проверяемый пользовательский контракт.
